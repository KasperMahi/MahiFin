# Implementation decisions — 14 October 2026

## Audit

- Clean specification-only repository; no inherited application code or dependencies.
- Windows execution host has no Swift/Xcode. Apple builds/tests must run on GitHub macOS; hardware results remain pending.
- Verified private GitHub repository and push permissions. No visibility changes, secrets or live server data.
- [Swiftfin main](https://github.com/jellyfin/Swiftfin) currently requires tvOS 26, iOS 18 and Jellyfin 12. Its MPL-2.0 source is not copied. Earlier implementations inform architecture only.
- [Official SDK](https://github.com/jellyfin/jellyfin-sdk-swift) is generated against newer server contracts. Use a small URLSession boundary against stable Jellyfin 10.10 endpoints instead of binding to generated 12-only models. Minimum handshake: 10.10; future majors pass the minimum-version check, but require live compatibility validation. Live 10.10/10.11/12 tests pending.
- API reference: Jellyfin controllers at [v10.10.7](https://github.com/jellyfin/jellyfin/tree/v10.10.7/Jellyfin.Api/Controllers). Implement public info, password/Quick Connect, items/views/resume/next-up, playback info and session reporting, watched/favourite and original download. Fixture tests inspect requests; no invented SDK signatures.
- Native AVKit supports conservative MP4/MOV H.264/HEVC + AAC/AC3/EAC3 routing. HDR, Dolby Vision, passthrough and 4K profiles require device testing. Unknown streams fail closed. No MKV blanket transcoding rule.
- Alternative capability stayed disabled until an official binary, exact pin, verified public API and retained license were selected. Continuation now enables the real VLCKit adapter described below; public-distribution materials remain a separate gate.
- [Google Cast integration](https://developers.google.com/cast/docs/ios_sender/integrate) requires receiver application ID, session callbacks and actual receiver status. [Jellyfin receiver](https://github.com/jellyfin/jellyfin-chromecast) needs a verified protocol/auth strategy. Continuation integrates the official SDK for discovery/session controls, while credential/media loading stays blocked for the specific reasons below. No fabricated connection.
- Cast source spike: upstream [web sender](https://github.com/jellyfin/jellyfin-web/blob/e7a146f4b5807d6367ef87f4b7aa30ec993eb317/src/plugins/chromecastPlayer/plugin.js) discovers receiver application ID from the signed-in user's Configuration.CastReceiverId, so do not hard-code a guessed household ID. Upstream [receiver message handler](https://github.com/jellyfin/jellyfin-chromecast/blob/43ab2aae4f1cadf3a7158b31d8b647e53f98c47a/src/components/maincontroller.ts) requires account authorization context, and [stream helper](https://github.com/jellyfin/jellyfin-chromecast/blob/43ab2aae4f1cadf3a7158b31d8b647e53f98c47a/src/helpers.ts) constructs query-token stream URLs. This is concrete receiver-auth/privacy and conversion-policy work, not a missing guessed constant. Next: discover configured ID, validate supported scoped authorization and prevent receiver-driven video conversion before enabling the official SDK adapter. No claim that upstream protocol has been hardware-tested here.
- [Background downloads](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background): iOS URLSession background identifier, delegate delivery, durable per-account manifest, authenticated original endpoint, cellular disabled by default, file protection and backup exclusion. Force quit recovery follows iOS limits; no promise of continued transfer after user termination.
- Opaque URLSession resume data may contain authorization headers: app-retained resume blobs use device-only Keychain, not JSON/files. iOS maintains its own protected background-session state. Resume after token renewal may fail once; failed-transfer retry builds a fresh authenticated request. Delegate task IDs prevent replaced-transfer callbacks from changing current records.
- Diagnostics use an allowlisted structured report (route/codecs/error categories) rather than trying to regex-redact arbitrary server text.
- Initial generated project used Apple frameworks and the local core package; continuation adds the pinned official SDKs described below. Generator is checked in; CI checks reproducibility.

## Correctness limits

Continuation: official VLCKit 4 at revision 2e0868f5ed40fe59cd92f377645fdcc260c6e759 selected over SwiftVLC (Swift 6.3 toolchain requirement) and GPL-default KSPlayer. Objective-C bridge uses verified pinned public headers for time, seek, drawable and track selection. VLC receives only original static/local file URLs, quiet logging mandatory. Native remains preferred; local engine precedes server conversion for its declared format set. Official nightly binary is checksum-pinned; both app targets and real synthetic MKV integration must pass CI before treating this milestone as compile-tested. Public binary distribution has an explicit corresponding-source/relinking license gate. VLCKit 4 exposes Stopped rather than a separate EOF delegate: completion requires natural stop near known duration; manual stop detaches delegate first. Validate seek/end/error behavior with hardware; unknown/early stop never marks watched.

Server conversion audit: Jellyfin 10.10.7 DynamicHlsController accepts VideoCodec=copy and EncodingHelper.GetVideoEncoder returns it directly; AllowVideoStreamCopy alone is only a permission and insufficient. Copy/audio modes use explicit copy, no resizing/bitrate/tone-map/deinterlace request and subtitles excluded from burn-in. HLS fMP4 requires live server/media compatibility tests. Video mode only constructs URL with a five-minute account/item/source grant from the actual Cancel/Accept dialog; never persisted/reused across episodes. Cleanup uses verified DELETE Videos/ActiveEncodings. Apple availableHDRModes probes eligible formats, not physical HDR output verification; no Dolby Vision profile inference.

## Cast continuation: precise external blocker and useful fallback

Official Google package 4.8.6 and GTMSessionFetcher 3.0.0 pinned for iOS 18 only. SDK activates only after explicit discovery action and authenticated user Configuration.CastReceiverId probe; no startup telemetry by MahiFin. Standard receiver IDs F007D354/6F511C87 verified in [upstream default migration](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Server/Migrations/Routines/20250420160000_AddDefaultCastReceivers.cs); declared receiver Bonjour services, custom IDs fail with remediation. Receiver connection/status/control comes from actual GCK callbacks, not a timer or assumed success. Raw SDK logger delegate drops messages. Profile switch/logout disconnects the selected receiver.

[Receiver maincontroller at audited revision](https://github.com/jellyfin/jellyfin-chromecast/blob/43ab2aae4f1cadf3a7158b31d8b647e53f98c47a/src/components/maincontroller.ts) logs the full custom-channel data object before processMessage, whose auth context includes accessToken. This conflicts directly with AGENTS.md "Log no secrets". Sender-side sanitization cannot remove the remote receiver log. Its normal PlayNow/subtitle stream-change pipeline can negotiate video conversion independently. Therefore this build sends NO Jellyfin credential-bearing custom messages or media URLs to that receiver. Actual discovery/session/reconnect and standard CAF controls of existing selected receiver media are implemented, but Jellyfin casting is not marked complete.

Exit: patch/validate receiver logging redaction, supported auth/token strategy and per-load/track/seek conversion constraints; obtain/validate registered deployed receiver revision/ID; then wire message namespace urn:x-cast:com.connectsdk and confirmed response state with real-device tests. No custom hosted receiver or third-party service is added silently. Google SDK/privacy/binary terms require distribution review; optional SDK discovery necessarily uses Google's Cast ecosystem. No automatic app analytics are added.

The initial native-only implementation issued no conversion streams. Continuation now wires the audited copy/audio/video URL paths into AVPlayer, with an expiring per-attempt grant checked before every video URL construction. Live server/ffmpeg behavior is still a required integration gate; compile/request tests are not server-execution evidence.

Static streaming is allowed only when metadata explicitly declares VideoFile (not BluRay/DVD or missing type). Upstream VideosController has a disc-source encoding branch even with Static=true, so fail closed before constructing that URL. Tests cover missing/disc type rejection. Original downloads are a separate byte endpoint and accept one unambiguous source.

History is durable per account, coalesced per item and retries absolute position/played state through nullable UpdateUserItemDataDto. Applied timestamp+state acknowledges a lost response without another mutation. Jellyfin has no general idempotency key for session posts: session activity is best effort, never described as exactly-once over a failed response. Playing/Progress/Stopped requests are serialized for each playback object; late generation callbacks are ignored. Offline conflict detection compares server LastPlayedDate against stable local activity timestamps; equal ambiguous or implausibly future dates retain a conflict. Missing LastPlayedDate permits upload (first playback); a known newer server date discards older queued activity. Favourites and play counts are not touched by offline replay. No cross-client compare-and-swap API is available.

Continuation history storage is one atomic state file containing the pending queue, local sequence and last activity snapshots. Successful acknowledgement removes only the matching queue UUID and retains offline resume. A newer server state can replace its matching snapshot, never a newer local event. Clock-conflict items remain pending while unrelated items sync. Legacy history/sequence files are read for migration; no previously acknowledged history can be recovered from the old queue-only format. Background transfer completion must equal the probed source size; HTTP 206 additionally requires a valid final range ending at the original size. Files/OS behavior still require physical-device validation.

Simulator evidence at 6b906ed: 24 core tests, both unsigned builds and real iOS synthetic MKV seek/EOF passed. tvOS XCTest failed to launch before assertions; boot synchronization/serialized destinations added rather than disabling tests. No blanket codec, subtitle rendering, remote control, HDR or audio output claim follows from this small synthetic clip.
